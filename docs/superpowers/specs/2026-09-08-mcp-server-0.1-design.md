# MCP Server 0.1: Design

**Date:** 2026-09-08
**Status:** Approved, ready for implementation planning
**Scope:** `graphql-api` (gitlab `oswatcher/graphql-api`) and `oswatcher-hub` (github `OSWatcher/oswatcher`)

## Goal

Bring the OSWatcher MCP server to a functional, validated 0.1 release: rebased onto the
post-Auth0 open-source `master`, exposing enough of the GraphQL API that an LLM can carry
out a complete OS investigation, and validated against a real corpus.

## Current state

The work exists on two branches:

| Repo | Branch | Pushed | Base | Position |
|---|---|---|---|---|
| `graphql-api` | `feat/mcp-server` | **No, local only** | `b1b9b57` (PR #65) | 10 ahead, 9 behind |
| `oswatcher-hub` | `wip/mcp-server` | Yes (origin) | `ade2f9d` (PR #122) | 1 ahead, 1 behind |

`graphql-api/feat/mcp-server` carries two things:

1. **`mcp/` subproject**: a standalone Node 25 ESM TypeScript MCP server using
   `@modelcontextprotocol/sdk` over Streamable HTTP (stateless), Express endpoints
   `POST /mcp` and `GET /health` on port 3001, a codegen-generated GraphQL SDK, jest tests

2. **Server-side paginated search**: `src/search-session.ts`, the `searchWithSession` and
   `searchNext` queries, the `searchClose` mutation, and the `PaginatedSearchResult` type.

`oswatcher-hub/wip/mcp-server` is a single commit adding an `mcp` service to

### What changed underneath

`origin/master` of `graphql-api` moved 9 commits ahead, and those commits removed the
entire auth model:

- `dda22be chore: remove Auth0 (#66)`, `115bbd7 chore: open-source readiness pass`
- `fcdfa48 chore: remove PostHog (#69)`, `5aa9265 feat: drop the CORS origin allow-list (#68)`
- `1f8ec91 chore: remove blob download branch restriction (#70)`

Verified on `origin/master`:

- `src/auth/` is gone; no `auth0`, `jwt`, `jose` or `oauth` dependency remains.
- HTTP context is `async ({ req }) => ({ req })` (`src/index.ts:335`); WebSocket context is
  `async () => ({})` (`src/index.ts:145`). There is no `jwt` in either.
- `diffNodesAt` has no auth gates: every `max_depth` value is allowed.
- `GET /blob/:hash` streams any blob from MinIO with no authorization check.

## Non-goals for 0.1

Recorded explicitly so they are not rediscovered as gaps:

- **Blob download and file contents.** Deferred. The oswatcher-hub PR #123 description
  mentions a separate Winbindex-based file-content thread, which looks like the 0.2 path.
- **Horizontal scaling of search sessions.** Documented as a constraint, not fixed.
- **A published MCP docker image.** 0.1 requires sibling source checkouts.
- **MCP resources, prompts and sampling.** 0.1 is tools only.
- **Authentication.** There is nothing to authenticate against.

## Decisions

### D1: Task-shaped read tools, thin tools kept as escape hatch

New read tools take `(ref, path, name)` and resolve the chain internally. The existing thin
hash-based tools (`traverse_path`, `get_winreg_root`, `diff_nodes`) are retained for
composition and for entity combinations the task-shaped tools do not reach.

This mirrors the split already present between `diff_versions` (resolves refs) and
`diff_nodes` (raw hashes). It partially reverses the previous "Do not collapse these steps"
rule in `CLAUDE.md`, which was written when the surface was diff-only.

Rationale: with thin tools alone, "show me the `_EPROCESS` layout in win11-24h2" costs five
round trips and dumps a multi-thousand-row `getBlobsWithSymbols` result into context to find
one blob hash.

### D2: Resolution logic lives in the MCP layer, not in new GraphQL resolvers

A `mcp/src/resolve.ts` helper composes existing GraphQL queries client-side. 0.1 adds no new
custom resolvers to `graphql-api` beyond the paginated-search code already on the branch.

Rationale: `graphql-api` master is a stable open-source artifact with a second consumer (the
frontend, which already composes these same queries client-side with an Apollo cache). The
MCP is the component in flux. Hops are localhost-cheap inside the compose network. The
alternative, adding `getStruct`/`listTree` resolvers, would grow the public schema purely for
MCP's benefit and require a separate resolver test suite.

### D3: The `include_updates` JWT gate is deleted, not adapted

`feat/mcp-server`'s `searchWithSession` resolver contains:

```ts
if (input.commit_range.include_updates === true && !context.jwt) {
    throw new Error("Commit traversal with include_updates requires authentication...");
}
```

Since `context.jwt` is now always `undefined`, `!context.jwt` is always `true`. Replaying
this unchanged ships a `search` tool that throws on every call passing `include_updates:
true`, and `include_updates` is a parameter the MCP `search` tool exposes to the LLM. This is
a release blocker, not cleanup. `include_updates` becomes unconditionally allowed.

### D4: Uniform pagination envelope over three mechanisms

Every paginated tool returns `{ items, has_more, next_cursor }`, so the LLM learns one
pattern. Underneath: search uses server-side sessions, `list_*` tools use Neo4j connection
cursors, `git_log` uses limit/offset.

`search_next` and `search_close` remain distinct tools because search sessions have a
lifecycle the others do not: they expire after 5 minutes of inactivity, connection cursors do
not. Each description states this in one line. Search's `results` field is renamed `items`
for consistency.

### D5: `search-session.ts` carries through the rebase unchanged

Sessions live in a process-local `Map`, so the API cannot be horizontally scaled while
sessions are in use. This is documented rather than fixed for 0.1. The pattern earns its
keep: `search` streams results from an async generator over a 6.9M-node graph, which cannot
be offset/limited.

## Tool surface

17 tools. 10 existing, 7 new.

### Retained unchanged

`list_branches`, `list_commits`, `diff_versions`, `search`, `search_next`, `search_close`,
`traverse_path`, `get_winreg_root`, `get_blobs_with_symbols`, `diff_nodes`.

`diff_nodes`, `traverse_path` and `get_winreg_root` gain a line in their descriptions:
"Prefer `get_struct` / `list_tree` / `list_registry_key` unless you need raw hash access."
Without it an LLM reaches for the low-level tool it encountered first.

### New

| Tool | Signature | Resolution chain (hops) |
|---|---|---|
| `list_tree` | `(ref, path, limit?, cursor?)` | resolveRef, traversePath, `child_trees`/`child_blobsConnection` (3) |
| `list_registry_key` | `(ref, hive, key_path, limit?, cursor?)` | resolveRef, traversePath(hive file), winreg root, traversePath(key), `child_keys`/`child_valuesConnection` (5) |
| `get_struct` | `(ref, blob_path, struct_name)` | resolveRef, traversePath, structByName, `fieldsConnection` (4) |
| `list_structs` | `(ref, blob_path, name?, limit?, cursor?)` | resolveRef, traversePath, `has_structConnection` (3) |
| `list_symbols` | `(ref, blob_path, name?, limit?, cursor?)` | resolveRef, traversePath, `has_symbolConnection` (3) |
| `git_log` | `(path, entity_type, commit_range, limit?, offset?, status_filter?, order?)` | 1:1 with `gitLog` (1) |
| `get_commit_capabilities` | `(ref)` | 1:1 with `getCommitExtractedDataLabels` (1) |

Notes:

- **`get_struct` is the highest-value addition.** Reading a struct today requires calling
  `diff_nodes` with the same hash on both sides plus `status_filter: ["UNCHANGED"]`, abusing
  a diff tool to perform a read.
- **`git_log` closes the largest capability gap.** "When did this entity last change, and
  across which update" is the question OSWatcher exists to answer, and the MCP currently
  cannot ask it.
- **`hive` is an enum**, `SAM | SECURITY | SOFTWARE | SYSTEM | DEFAULT`, mapped internally to
  `/Windows/System32/config/*`. An LLM knows `HKLM\SOFTWARE`; requiring it to know the
  on-disk hive location is a memorisation tax.
- **By-name lookups are merged into the list tools.** The frontend has separate
  `FetchSymbolByName` / `FetchStructByName` queries, but `list_symbols(ref, blob_path,
  name?)` with optional exact-match edge filtering (`where: { edge: { name: $name } }`)
  covers both cases in one tool.
- `list_commits` is retained alongside `git_log`. They answer different questions: which
  snapshots exist, versus what changed at a path.

All task-shaped tools take `ref` (branch name or 40-character commit hash) as their first
argument and absolute paths beginning with `/`. That uniformity is what lets an LLM
generalise from one tool to the next.

### Composite cursors for two-connection tools

`list_tree` and `list_registry_key` each paginate two connections at once
(`child_trees` + `child_blobs`, and `child_keys` + `child_values`), but the D4 envelope
exposes a single `next_cursor`. Resolution: `limit` applies **per connection**, and
`pagination.ts` encodes both underlying `endCursor` values into one opaque composite cursor
that the LLM passes back unchanged. `has_more` is the OR of the two `hasNextPage` flags. A
connection that is already exhausted is simply not requested on the next page.

Response shapes stay structured rather than flattened, because the distinction matters to
the caller:

```
list_tree         -> { directories: [{name, hash}], files: [{name, hash}], has_more, next_cursor }
list_registry_key -> { subkeys: [{name, hash}], values: [{name, type, value}], has_more, next_cursor }
```

The read query shapes are all proven by the frontend's `src/queries.ts`
(`~/Projets/frontend`), including connection cursor pagination (`first`/`after`,
`pageInfo.endCursor`, `totalCount`) and edge-name filtering.

## Architecture

### Module layout

`mcp/src/server.ts` is 545 lines for 10 tools, of which roughly 340 are a copy-pasted
try/catch and `JSON.stringify` envelope repeated per handler. At 17 tools that becomes ~580
lines of duplication.

Restructure:

- Each `mcp/src/tools/*.ts` exports `{ name, description, schema, handler }`, co-locating the
  long tool descriptions with the code they describe.
- `mcp/src/server.ts` becomes a manifest that iterates the tool modules and applies the
  content/error envelope once. Target: under 100 lines.
- **New** `mcp/src/resolve.ts`: `resolveRef`, `resolveTreeHash(ref, path)`,
  `resolveBlobHash(ref, path)`, `resolveHiveRoot(ref, hive)`. This is where D2's multi-hop
  chains live, used by five or more tools. `tools/resolve-ref.ts` moves here; it was never a
  registered tool, only an internal helper in the wrong directory.
- **New** `mcp/src/pagination.ts`: the D4 envelope. Normalises connection `pageInfo`,
  `gitLog` offsets and search sessions into one shape.

### Client simplification

`mcp/src/graphql/client.ts` forwards the incoming `Authorization` header to the GraphQL API.
Against an unauthenticated API this is dead weight: drop it, and hoist SDK construction to
module scope since it becomes request-invariant. `createServer(sdk)` stays per-request,
because an `McpServer` binds to a single transport on `connect`.

## Testing

### Layer 1: unit (jest + nock)

Extends the existing `mcp/tests/*.test.ts` pattern. One test file per new tool, plus
dedicated files for `resolve.ts` and `pagination.ts`, which carry the multi-hop logic and are
therefore where bugs will live.

Two tests assert the **outgoing request body**, which is the honest use of a mock:

- filesystem diffs send `filter: ["Tree", "Blob"]`
- struct and symbol diff paths send `max_depth: 1`

### Layer 2: live end-to-end

`docker compose up -d` in oswatcher-hub auto-seeds the corpus since PR #123 merged
(2.4 GB dump, 6,960,880 nodes, 41,413,801 relationships). Bring the stack up with the rebased
`mcp` service, attach with:

```
claude mcp add --transport http oswatcher http://localhost:3001/mcp
```

then drive the acceptance scenarios below, recording for each: the tool calls made, the
round-trip count, **whether the LLM picked the right tool unaided**, and result sanity. That
third column is the real test of the tool naming and description work.

Results are recorded in `docs/reference/mcp-validation-0.1.md`.

## Acceptance criteria

| # | Scenario | Exercises |
|---|---|---|
| 1 | What OS versions are tracked? | `list_branches` |
| 2 | What is in `/Windows/System32/drivers`? | `list_tree` |
| 3 | Show `_EPROCESS` in `ntoskrnl.exe` | `get_struct`, expect ~261 fields |
| 4 | How did `_EPROCESS` change 24h2 to 25h2? | `diff_nodes` with `max_depth: 1` |
| 5 | What is under `HKLM\SOFTWARE\...\Run`? | `list_registry_key` |
| 6 | Registry diff across versions | `traverse_path`, `get_winreg_root`, `diff_nodes` |
| 7 | Address of `NtCreateFile` in `ntdll.dll` | `list_symbols(name=...)` |
| 8 | When did `ntdll.dll` change? | `git_log` |
| 9 | Search "Defender", page through results | `search`, `search_next` |
| 10 | Filesystem diff at `/` between two commits | `diff_versions` |

**Scenarios 3, 4 and 10 must assert non-empty results, not merely absence of an exception.**
Both bugs that already bit this branch fail by returning a plausible empty list: the empty
`filter` silently drops Blob leaf nodes, and a missing `max_depth: 1` makes Struct diffs
return nothing. A test checking only for absence of errors passes against both. This is
precisely why mocked tests alone cannot validate 0.1.

**0.1 is done when:** the branch is rebased and merged, 17 tools are registered, unit tests
pass including the two gotcha regressions, and all 10 scenarios have been run live against
the seeded corpus with results recorded.

## Delivery sequence

### Step 0: two probes

1. `git push -u gitlab feat/mcp-server`, so the rebase has a recoverable point.
2. Bring the seeded corpus up and verify it contains PDB data: run `getBlobsWithSymbols` on a
   branch and confirm `_EPROCESS` resolves. Scenarios 3, 4 and 7, a third of the acceptance
   list and the entire justification for `get_struct`, depend on symbol and struct data being
   present in the dump. If it is filesystem-and-registry only, the tool priorities change,
   and that must be known before the tools are written.

### graphql-api (gitlab): four PRs

1. **Rebase onto master.** Three collapsed commits, no new tools. Shippable alone: it answers
   "do the existing 10 tools still work with auth gone?" without new-feature noise.
2. **Refactor.** Tool manifest, `resolve.ts`, `pagination.ts`. No behaviour change; the
   existing suite is the proof. Kept separate from PR 3 because a refactor tangled with new
   features cannot be reviewed as a refactor.
3. **The 7 new tools**, their tests, and docs.
4. **Validation.** The scenario run, `docs/reference/mcp-validation-0.1.md`, and whatever
   fixes the live run surfaces.

### oswatcher-hub (github): one PR

Rebase `wip/mcp-server` (1 commit) onto master, which has moved by one (the db-seed merge),
and rename the branch `feat/mcp-server`. Un-WIP only after graphql-api PR 1 lands, since that
is when `../graphql-api/mcp/` exists.

The compose service builds from a **sibling checkout** (`context: ../graphql-api`), so
`graphql-api` and `oswatcher-hub` must be adjacent on disk. Acceptable for development, but
it means the MCP cannot be run without a source checkout. A published image is a 0.2 concern.

## Risks

| Risk | Mitigation |
|---|---|
| The seeded corpus may lack PDB/struct data, invalidating scenarios 3, 4 and 7 | Step 0 probe, before any tool is written |
| The corpus dump is a Dropbox link throttled at roughly 20 GB/day (about 8 downloads) | Seed once and snapshot the volume rather than recreating it per test run |
| `@modelcontextprotocol/sdk ^1.12.1` and `node:25-alpine3.22` both date from March 2026 | Version check during the rebase, not mid-validation |
| 17 tools with partially overlapping semantics create tool-choice noise | The escape-hatch pointer lines, plus the "picked the right tool unaided" column in the validation run |
